## Нагрузочная проверка

На отдельной тестовой БД созданы 500 пользователей с отдельными JWT и сеансами. 500 одновременно работающих HTTP-клиентов выполнили по три авторизованных запроса списка чатов с паузами 1 секунда.

| Показатель | Результат |
|---|---:|
| Клиентов | 500 |
| Запросов | 1500 |
| Ошибок | 0 |
| Общее время | 5,23 с |
| Медиана ответа | 218,4 мс |
| 95-й процентиль | 1646,0 мс |
| Максимум | 1805,3 мс |

При первом прогоне обнаружено ожидание пула БД, занимавшее потоки обработчиков. После переноса ожидания в асинхронный семафор повторный прогон дал приведённый результат.

Проверка имитирует авторизованный polling, а не 500 полноценных браузеров с шифрованием и передачей файлов. Она не доказывает скорость доставки всех сообщений под любой нагрузкой. В отдельном браузерном сценарии время от отправки до появления у адресата, включая открытие чата, составило 161 мс; это результат локального замера, а не гарантия для внешней сети.

## Что ещё требует длительных или внешних испытаний

- 24 часа непрерывной стабильной работы из раздела 5.4 ТЗ не проверены.
- Месячная доступность 90% не может быть установлена коротким тестом.
- Яндекс Браузер отдельно не проверялся; выполнены проверки Google Chrome и мобильного размера окна.
- Восстановление проверено на небольшой демонстрационной БД; часовой норматив для большой БД требует отдельного замера.
- Перед вводом в корпоративную сеть нужны доверенный TLS-сертификат, собственные учетные записи и проверка модели угроз.

Учебные ограничения описаны в README и руководстве разработчика: polling, отсутствие автоматической ротации ключей и прямой секретности, лимит файлов 8 МБ, открытые метаданные. Формальных актов приемки и утверждений о сертификации не создавалось.

## Повторение

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\test.ps1
docker compose exec -T app sh -c 'DATABASE_URL="${DATABASE_URL%/*}/messenger_test" python -m scripts.load_test'
powershell -ExecutionPolicy Bypass -File .\scripts\verify_backup.ps1
```

Первый скрипт пересоздаёт **только** БД `messenger_test`. Нагрузочный сценарий добавляет пользователей только в неё. Проверка резервирования пересоздаёт отдельную `messenger_restore_check` и сохраняет свежий снимок рабочей учебной БД как `backups/demo.dump`. Не запускайте сравнение резервной копии одновременно с изменением рабочих данных: копия является снимком на момент выгрузки.
